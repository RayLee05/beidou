## 本机 SSH 配置

下列为本机已验证配置的等价片段；不要覆盖其他项目的 Host 记录或已有密钥：

```sshconfig
Host vm-ic vm-ic-nat
    HostName 10.156.34.48
    Port 2222
    User 7902_13
    IdentityFile ~/.ssh/id_rsa_vm_ic
    IdentitiesOnly yes
    HostKeyAlgorithms +ssh-rsa
    PubkeyAcceptedAlgorithms +ssh-rsa
    HostKeyAlias 10.156.34.6
    StrictHostKeyChecking yes
    ServerAliveInterval 20
    ServerAliveCountMax 3
    TCPKeepAlive yes
    ConnectTimeout 12
    ConnectionAttempts 1
```

`HostKeyAlias 10.156.34.6` 只是复用本机已核实的旧 known_hosts 主机密钥，**实际网络连接仍是 10.156.34.48:2222**。队友若没有旧 known_hosts 记录，不要直接复制该行后关闭校验：应先核对上述主机指纹，正常建立自己的 known_hosts 信任。旧版客户端如不识别 `PubkeyAcceptedAlgorithms`，可使用旧名称 `PubkeyAcceptedKeyTypes`。

队友每台电脑生成并授权自己的 RSA 密钥，仅追加公钥到 Linux `~/.ssh/authorized_keys`，目录/文件权限为 700/600；不要共享私钥、覆盖已有授权，也不把密码写进脚本或文档。

## 已提供的脚本

- [remote.py](../logic_synth/scripts/remote.py)：在本机打包、提交、查询、取回结果；不存储密码或私钥，沿用 `vm-ic` 配置并严格验证主机密钥。
- [job.sh](../logic_synth/scripts/job.sh)：在远端核验源码，后台执行 DC 并记录退出码、日志和资源；使用锁和 PID 标记，重复 start 只查询，避免重复启动。
- [audit_libraries.sh](../logic_synth/scripts/audit_libraries.sh)：只读核查指定库目录；原始包结论须有成功完成的日志。

在仓库根目录使用唯一新 job 名：

```powershell
python logic_synth/scripts/remote.py pack --job core-channel-YYYYMMDD-vN
python logic_synth/scripts/remote.py submit --job core-channel-YYYYMMDD-vN
python logic_synth/scripts/remote.py status --job core-channel-YYYYMMDD-vN
python logic_synth/scripts/remote.py fetch --job core-channel-YYYYMMDD-vN
```

上述专用脚本默认沿用 `vm-ic`，本机别名更新后即走 NAT 中转，无需修改 Python 或 DC 脚本。不要将它与原项目的 `scripts/vm_remote.py`、`scripts/dc_synth.tcl` 混用；专用工程默认顶层是 `bds_channel`，六路核心使用 `pack --top bds_bb_6ch_core`，恢复任务时仍须按实施计划确认运行范围。

`submit` 完成传包、解包、源码核验和后台启动后即返回。关闭本机终端后不必保留连接；之后查询/取回仍需一次成功认证。不要因查询失败就换新名字重复提交同样设计。本机 `reports/remote/<job>/manifest.json` 保存准确远端目录、host 别名和源码校验值，任务修改后重新打包。

注意：`--host` 对 pack 时写入的 manifest 生效；后续 submit/status/fetch 读取 manifest 中的 host。旧 manifest 若记录 `vm-ic`，会自动使用本机新的中转配置；若记录旧 IP 或其他别名，不能仅在 status/fetch 命令后加 `--host` 就认为切换成功，应先核查记录，保留原快照及作业身份，避免误提交。

连接恢复后，优先查询已有作业（只读操作，不重新 submit）：

```powershell
python logic_synth/scripts/remote.py status --job core-channel-20261102-v1
```

历史作业 `core-channel-20261102-v1` 经单次 SSH 上传、SHA256 核验，以 `nohup + setsid` 启动，后来以 137 结束。这个执行/资源问题仍需单独排查，连接修复不改变原结论；不能与原项目 `stable-dc-20261012b` 的示例库成功结果混为一谈。

## 只有图形客户端或虚拟机控制台可用时

如果 WinSCP、MobaXterm、已有实验室终端或虚拟机控制台可以正常登录，可用它们将本机 `reports/remote/<job>/source.tgz` 上传到个人目录下新建的独立作业目录。所有操作均使用同一授权账号，保持原包的目录结构。核对 `manifest.json` 中的 archive SHA256 后，在该作业目录解包：

```bash
sha256sum source.tgz
tar xzf source.tgz
sha256sum -c SOURCE_SHA256SUMS
bash logic_synth/scripts/job.sh start
bash logic_synth/scripts/job.sh status
```

确认 SHA256 与本机记录一致后才执行后续步骤。`start` 已在脚本内部处理 `nohup/setsid`，不要再另起一次 DC。日志在 `job_state/` 与 `logic_synth/logs/`，结果在 `logic_synth/reports/` 和 `logic_synth/output/`。

这类方式能换传包入口或利用已登录会话，但服务器对同一账号拒绝认证时，换客户端本身通常不能消除认证问题。2026-11-02 通过系统 OpenSSH、显式 RSA 兼容设置、直连、两把已有 RSA 密钥及 Paramiko 的尝试曾出现成功后再次拒绝，属于旧直连方式的历史记录。当前采用上述 NAT 中转路径。密码不写入项目或脚本，也不关闭主机指纹校验。

若今后再次异常，应从实验室控制台核对 NAT 地址、转发目标、账号/公钥权限、认证限制和资源状态，不能把旧桥接 IP 冲突当作所有错误的已确认原因。脚本解决任务对会话的依赖，认证和服务器资源仍须分别处理。配置过程与最新连接摘要见 [当前连接说明](../docs/SSH_CONNECTION_CURRENT.md)。
